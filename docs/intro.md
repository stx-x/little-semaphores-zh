# 导论

<div class="chap-en">Introduction</div>

日常用语里，「同步」指的是让两件事同时发生。在计算机系统中，同步的含义要更宽泛一些：它指的是事件之间的关系——任意数量的事件，以及任意种类的关系（之前、期间、之后）。

程序员常常关心的是**同步约束**（synchronization constraints），也就是对事件先后顺序提出的要求。例如：

串行化：

:   事件 A 必须发生在事件 B 之前。

互斥：

:   事件 A 和事件 B 不能同时发生。

在现实生活中，我们通常借助时钟来检查和落实同步约束。我们怎么知道 A 是否发生在 B 之前？只要知道两个事件各自发生的时刻，比一比时间就行了。

在计算机系统中，我们常常需要在没有时钟可依靠的情况下满足同步约束，原因要么是不存在统一的时钟，要么是我们无法以足够精细的分辨率得知事件发生的时刻。

这正是本书的主题：用软件技术来落实同步约束。

## 执行模型

要理解软件同步，你必须对计算机程序如何运行有一个模型。在最简单的模型里，计算机一条接一条地顺序执行指令。在这个模型下，同步是件微不足道的事：只要看程序就能判断事件的先后顺序。如果语句 A 出现在语句 B 之前，那么 A 就会先执行。

有两种情况会让事情变得复杂。一种可能是计算机是并行的，也就是说它有多个处理器同时运行。这时就不容易判断一个处理器上的语句是否先于另一个处理器上的语句执行。

另一种可能是单个处理器上运行着多个执行线程。线程是一串顺序执行的指令。如果有多个线程，处理器可以先运行其中一个一段时间，然后切换到另一个，如此往复。

一般来说，程序员无法控制每个线程何时运行，这些决定由操作系统（具体说是调度器）做出。于是同样地，程序员也无法判断不同线程中的语句会在何时执行。

就同步而言，并行模型与多线程模型没有区别。问题是一样的：在单个处理器（或单个线程）内部，我们知道执行顺序；而在处理器（或线程）之间，则无从判断。

一个现实中的例子也许能说明得更清楚。设想你和朋友 Bob 住在不同的城市，某天临近晚饭时，你开始琢磨：那天中午，你和 Bob 谁先吃的午饭？你怎么才能弄清楚？

显然，你可以打电话问他几点吃的午饭。但如果你按自己的钟 11:59 开始吃，而 Bob 按他的钟 12:01 开始吃呢？你能确定谁先开始吗？除非你们俩都非常小心地校准了各自的时钟，否则你无法确定。

计算机系统面临同样的问题，因为即便它们的时钟通常很准，精度总归是有限的。此外，大多数时候计算机根本不记录事情发生的时刻。发生的事情太多、太快，无法为每件事都记下准确时间。

**问题**：假设 Bob 愿意听从简单的指示，有没有办法能*保证*明天你会比 Bob 先吃午饭？

## 用消息实现串行化

一个办法是嘱咐 Bob，在你打电话之前不要吃午饭。然后，确保你自己吃完午饭之后才打电话。这个做法看似平淡无奇，但它背后的思想——消息传递——是许多同步问题的真正解法。冒着啰嗦之嫌，我们来看这样一条时间线。

```python title="Thread A (You)"
Eat breakfast 
Work          
Eat lunch     
Call Bob
```

```python title="Thread B (Bob)"
Eat breakfast
Wait for a call
Eat lunch
```

第一列是你执行的一系列动作，也就是你的执行线程。第二列是 Bob 的执行线程。在一个线程内部，我们总能判断事情的先后顺序。我们可以用如下式子表示事件的顺序：

$$
\begin{aligned}
a1 < a2 < a3 < a4  \\
b1 < b2 < b3
\end{aligned}
$$

 其中关系 $a1 < a2$ 表示 a1 发生在 a2 之前。

不过一般来说，来自不同线程的事件是无法比较的；例如，我们完全不知道谁先吃的早饭（是 $a1
< b1$ 吗？）。

但借助消息传递（那通电话），我们*确实*能判断谁先吃午饭（$a3 < b3$）。假设 Bob 没有别的朋友，那么在你打电话之前他不会接到任何电话，因此 $b2 > a4$。把所有关系合起来，我们得到 

$$
\begin{aligned}
b3 > b2 > a4 > a3
\end{aligned}
$$

 这就证明了你的午饭先于 Bob。

在这个例子里，我们会说你和 Bob 是**顺序地**（sequentially）吃午饭的，因为我们知道事件的先后顺序；而你们是**并发地**（concurrently）吃早饭的，因为我们不知道。

谈到并发事件时，人们容易说它们是在同一时间、或者说同时发生的。作为简略说法这没问题，只要你记住严格的定义：

> 如果仅凭看程序无法判断两个事件谁先发生，那么这两个事件就是并发的。

有时候程序运行之后我们能判断谁先发生，但很多时候判断不了；即便能判断，也无法保证下一次运行会得到同样的结果。

## 不确定性

并发程序常常是**不确定的**（non-deterministic），意思是仅凭看程序无法判断它执行时会发生什么。下面是一个简单的不确定性程序的例子：

```python title="Thread A"
print "yes"
```

```python title="Thread B"
print "no"
```

由于两个线程并发运行，执行顺序取决于调度器。在程序的任何一次运行中，输出可能是 "yes no"，也可能是 "no yes"。

不确定性正是并发程序难以调试的原因之一。一个程序可能连续 1000 次正确运行，却在第 1001 次崩溃，这取决于调度器当时的具体决定。

这类 bug 几乎不可能通过测试发现，只能靠谨慎的编程来避免。

## 共享变量

大多数时候，大多数线程中的大多数变量都是**局部**的（local），也就是说它们属于某个线程，其他线程无法访问。只要情况如此，通常就没什么同步问题，因为线程之间根本不交互。

但通常会有一些变量被两个或更多线程**共享**（shared），这是线程之间相互影响的方式之一。例如，线程之间传递信息的一种方式，就是让一个线程读取另一个线程写入的值。

如果线程之间没有同步，那么仅凭看程序，我们无法判断读者读到的会是写者写入的值，还是那里原有的旧值。因此许多应用会强制这样的约束：读者在写者写入之前不得读取。这正是[串行化](#serialization)一节所讨论的串行化问题。

线程之间交互的其他方式是并发写（两个或更多写者）和并发更新（两个或更多线程执行一次读后跟一次写）。接下来两节讨论这些交互。共享变量的另一种可能用法——并发读——一般不会引发同步问题。

### 并发写

在下面的例子中，`x` 是由两个写者访问的共享变量。

```python title="Thread A"
x = 5
print x
```

```python title="Thread B"
x = 7
```

会打印出什么 `x` 值？当所有这些语句都执行完之后，` x` 的最终值是多少？这取决于语句执行的顺序，我们称之为**执行路径**（execution path）。一条可能的路径是 $a1 < a2 < b1$，此时程序的输出是 `5`，但最终值是 `7`。

**问题**：哪条路径会得到输出 `5`、最终值 `5`？

**问题**：哪条路径会得到输出 `7`、最终值 `7`？

**问题**：有没有哪条路径会得到输出 `7`、最终值 `5`？你能证明吗？

回答这类问题是并发编程的重要部分：哪些路径是可能的，可能产生哪些效果？我们能否证明某个（期望的）效果必然出现，或者某个（不期望的）效果不可能出现？

### 并发更新

更新是一种这样的操作：读取变量的值，根据旧值算出新值，再写入新值。最常见的更新是自增，即新值等于旧值加一。下面的例子展示了共享变量 `count` 被两个线程并发更新。

```python title="Thread A"
count = count + 1
```

```python title="Thread B"
count = count + 1
```

乍一看，这里似乎并没有什么同步问题。只有两条执行路径，而它们的结果相同。

问题在于，这些操作在执行之前会被翻译成机器语言，而在机器语言中，更新需要两步：一次读和一次写。如果我们用临时变量 `temp` 重写这段代码，问题就明显多了。

```python title="Thread A"
temp = count
count = temp + 1
```

```python title="Thread B"
temp = count
count = temp + 1
```

现在考虑下面这条执行路径

$$

a1 < b1 < b2 < a2

$$

假设 `count` 的初始值是 `0`，它的最终值是多少？因为两个线程读到的是同一个初始值，所以它们写入的也是同一个值。这个变量只自增了一次，这恐怕不是程序员的本意。

这类问题很微妙，因为仅看一个高层程序，并不总能判断哪些操作是一步完成的、哪些操作可能被打断。事实上，有些计算机会提供由硬件实现、不可被打断的自增指令。不可被打断的操作被称为**原子的**（atomic）。

那么，如果我们不知道哪些操作是原子的，该怎么写并发程序呢？一种做法是收集每种硬件平台上每个操作的具体信息。这种做法的缺点显而易见。

最常见的替代做法是采取保守假设：所有更新和所有写操作都不是原子的，并用同步约束来控制对共享变量的并发访问。

最常见的约束是互斥（mutual exclusion），或称互斥锁（mutex），我在[同步](#synch)一节中提到过。互斥保证同一时刻只有一个线程访问共享变量，从而消除本节提到的这类同步错误。

**问题**：假设有 100 个线程并发运行下面这个程序（如果你不熟悉 Python，`for` 循环会把更新执行 100 次）：

    for i in range(100):
        temp = count
        count = temp + 1

当所有线程都完成之后，`count` 可能的最大值是多少？可能的最小值是多少？

提示：第一个问题很简单，第二个不简单。

### 用消息实现互斥

与串行化一样，互斥也可以用消息传递来实现。举例来说，设想你和 Bob 共同管理一座核反应堆，你们各自在远端站点监控。大多数时候，你们俩都盯着警示灯，但你们都可以抽空去吃午饭。谁先吃午饭无所谓，但你们绝不能同时去吃午饭，把反应堆丢下无人看管——这一点至关重要！

**问题**：设计一套消息传递（打电话）的方案来落实这些限制。假设没有时钟，你无法预知午饭何时开始，也无法预知它会持续多久。最少需要多少条消息？
